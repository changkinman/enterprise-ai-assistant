# 多意图任务规划设计

## 目标

将制度（general）、IT（technical）、财务（billing）、账户（account）四个领域从单标签路由升级为任务级路由：系统能够区分单任务、可并行的多任务、有依赖的多任务和需要澄清的歧义请求。

## 决策模型

`IntentRecognizer` 提供四领域候选分数和修饰属性；`TaskPlanner` 将复杂请求拆为带原文证据、主体、动作和依赖关系的任务；`AgentOrchestrator` 按 `TaskPlan.mode` 执行。候选分数只决定是否需要拆分，不能直接决定并行。

`parallel` 仅适用于不同领域、证据片段不同、没有依赖且不包含写入副作用的任务。相同证据片段的跨领域候选视为歧义并澄清；存在 `depends_on` 的任务按拓扑顺序串行执行。

## 兼容与失败语义

保留既有 `IntentResult` 和单意图 `run()` 调用方式。新增任务规划失败时不并行：候选明确时降级为单任务，候选不明确时返回澄清问题。澄清状态以会话为单位短期保存，用户下一轮补充会与原始消息重新规划。

## 数据结构

`BusinessDomain`：`general`、`technical`、`billing`、`account`。

`DomainCandidate`：领域、分数、证据片段。

`PlannedTask`：任务 ID、领域、原文证据、主体、动作、可信度、依赖任务 ID、修饰属性。

`TaskPlan`：执行模式（`single`、`parallel`、`sequential`、`clarify`）、任务、澄清问题和可持久化的待澄清状态。

## 验收场景

1. “VPN 登录不上，同时报销单被退回了”生成 IT 与财务两个独立任务，并行。
2. “先查报销单状态；如果被退回，再告诉我补什么材料”生成有依赖的任务，串行。
3. “报销系统退回了，怎么办？”中两个领域共享同一证据片段，返回澄清，不并行。
4. 低可信候选返回澄清。
5. 首轮澄清后，第二轮补充会与原始问题一起重新规划。
