# 文档命名、版本与知识库管理规范

> 版本：V1.0｜适用对象：创建、编辑、审核、发布或维护公司文档的员工。

## 1. 命名规则

在实际工作中，本节内容应作为后续流程的判断基础。员工遇到新情况时，先确认目标、事实和影响，再选择对应的处理方式；管理者应确保相关说明能够被员工找到、理解并执行。

文档标题和开头应直接回答读者“这是什么、适用于谁、什么时候使用”。如果员工必须先读很多背景才能知道是否相关，搜索和使用效率都会下降。

文档和知识库的价值在于让员工找到可信、可理解、可执行的信息。命名、版本和归档是基础，但正文还应让读者知道适用范围、前置条件、操作步骤、异常处理、责任人和下一步入口。

文件名应包含主题、业务范围、版本或日期等必要信息，使用清晰统一的分隔符，避免“最终版、最终版2、最新”等无法判断状态的命名。

推荐格式：`业务主题_文档类型_版本或日期`，例如：`报销流程_员工指南_V1.2`。

## 2. 版本管理

具体适用时，应结合岗位、业务场景和风险程度判断，不宜只看表面形式。规则发生变化或现有说明无法覆盖时，及时向指定负责人确认，并把已经确认的处理方式记录下来，避免不同人员重复猜测。

版本管理不仅记录修改次数，还要帮助使用者判断当前内容是否有效。涉及流程、权限、费用或系统入口的变更，应在正文或变更说明中明确影响和生效时间。

本规范适用于制度、流程、操作指南、知识说明、项目记录和对外资料。不同类型文档可以使用不同结构，但都应有明确作者、业务负责人、更新时间和来源。涉及财务、法务、隐私和安全的内容，应安排对应专业人员审核。

重大内容变更应升级版本号并记录变更说明、作者、审核人和生效日期。草稿、审核中、已发布和已废止状态应清晰标注，废止文档不得继续作为现行依据。

## 3. 审核与发布

为便于落地，相关人员应明确谁提出、谁审批、谁执行、谁复核以及出现问题时找谁。流程运行一段时间后，根据员工反馈和实际异常补充说明，让制度逐步适应真实工作。

文档负责人应把用户反馈看作维护输入，而不是把重复提问归结为员工不认真阅读。常见问题往往说明前置条件、例外场景或入口说明还不够清楚。

作者负责内容准确和及时更新，业务负责人负责确认规则与流程，文档维护人负责版本、权限、标签和入口，使用者负责反馈过期或不清晰内容。文档发布后并不是永久有效，应根据系统、政策和业务变化进行复审。

制度、流程和对外资料应由业务负责人审核；涉及法律、财务、隐私或安全的内容，应增加相应专业审核。发布前检查链接、附件、敏感信息和适用范围。

## 4. 知识库维护

命名时使用员工实际会搜索的主题、系统和场景词，版本变化记录修改原因和影响。发布前检查链接、附件、敏感信息和示例，过期内容标记废止而不是继续作为当前依据。

知识库文档应设置主题标签、适用部门、更新时间和来源。发现重复、过期、矛盾或无法追溯来源的内容，应提交维护工单，不直接覆盖正式文档。

## 5. 检查清单

- [ ] 文件名符合统一规则
- [ ] 文档状态和版本清晰
- [ ] 业务负责人已审核
- [ ] 敏感信息已检查
- [ ] 来源、标签和更新时间已登记

**文档结构建议：**

操作类文档建议先写适用范围和目标，再写前置条件、步骤、例外、负责人和检查清单。制度类文档应说明规则、禁止事项、审批关系和违规处理。知识说明类文档应提供定义、背景、示例、常见问题和来源，避免只有结论而没有上下文。

**版本号和变更说明：**

小范围文字修正可以增加修订号；流程、权限、责任人或外部要求发生变化时，应提升版本并重新审核。变更说明至少写清修改日期、修改人、变更内容和影响范围。不要通过复制文件创建多个“最终版”，统一在受控位置维护正式版本。

**审核发布流程：**

作者完成草稿后，先进行自检，再提交业务负责人审核。审核人应关注准确性、可执行性、适用范围、敏感信息和与现有制度的冲突。发布时设置生效日期和失效或复审日期，并通知真正需要使用的人，而不是只把链接放进大群。

**知识库内容维护：**

每篇知识库文档应有负责人和复审周期。出现政策变化、系统改版、流程异常、用户频繁反馈或文档与实际操作不一致时，应提前复审。重复内容应合并，冲突内容应明确以哪个来源为准，过期内容应标记废止而不是静默删除。

**搜索和使用体验：**

标题和小标题应使用员工实际会搜索的词，正文中适当包含同义词、系统名称和常见问法。重要步骤使用编号，关键限制使用提示语。长文档可以增加目录和“快速结论”，但不能用摘要替代完整流程和例外说明。

**常见问题：**

- **多人同时修改**：由负责人确定主版本，其他修改先合并后发布。
- **来源无法确认**：暂标记待核实，不把未经确认的内容作为正式制度。
- **文档内容冲突**：保留冲突证据，联系业务负责人和制度所有者共同确认。
- **员工找不到文档**：补充标签、别名、链接和入口说明，而不是重复上传相同副本。

**落地建议：**

每个部门最好指定一名文档维护联系人，负责过期提醒、权限申请和问题收集。员工提交新文档时，先搜索是否已有相近内容，能更新旧文档就不要新建副本。知识库维护的重点不是数量，而是员工能找到可信、易懂并且与实际操作一致的答案。

**员工自查：**

发布前检查标题、版本、来源、适用范围和敏感信息；修改后确认链接和示例仍可用。发现文档与实际流程不一致时，标记问题并通知负责人，不要继续复制过期内容。

**复盘与改进：**

根据搜索失败、重复提问和文档反馈，持续调整标题、标签、示例和入口，让知识库真正服务于日常工作。

文档首先要服务于实际使用者，而不是只满足作者记录过程的需要。操作文档应让员工知道适用范围、前置条件、步骤、结果和异常处理；制度文档应说明责任、审批、禁止事项和生效范围；知识说明应解释概念、背景、示例和来源。不同类型的文档不要使用完全相同的写法。

命名时尽量使用员工会搜索的业务词、系统名和场景词。文件名应避免“最终版、最新、临时”等无法长期判断状态的词，版本和日期按统一规则填写。文件移动、改名或合并时同步更新入口链接，避免知识库里出现大量失效地址。

版本变更需要说明修改原因和影响范围。小的错别字修正可以简单记录，流程、权限、责任人、费用标准和外部要求变化则应重新审核。草稿、审核中、已发布和已废止状态要明显区分，过期文档不能继续被搜索结果误导员工。

审核人不只检查文字是否通顺，还要确认步骤是否能执行、例外情况是否覆盖、示例是否脱敏、链接是否有效、内容是否与其他制度冲突。涉及财务、法务、隐私和安全的文档应邀请对应专业人员参与，不要由作者一个人判断全部风险。

知识库需要负责人和复审周期。系统改版、政策变化、用户频繁反馈、重复提问或实际流程与文档不一致时，应提前复审。重复内容可以合并，冲突内容应明确主来源，已经废止的内容应保留必要历史记录并标注不可作为当前依据。

维护知识库时可以观察搜索失败、无结果问题、点击后退出和用户反馈，但不要只用文档数量衡量效果。真正有价值的是员工能否在需要时找到可信答案，并能按照步骤完成任务。每次维护后最好由一名不了解背景的员工试读，检验是否仍有隐含前提。

写作时先确定读者和使用场景。给新员工看的指南需要解释背景和常见词，给熟悉业务的人员看的操作说明可以更直接，但仍要写清前置条件和异常处理。不要把不同受众、不同系统和不同版本的内容混在一篇文档中，避免正文过长却无法快速找到答案。

步骤类文档中的动词要明确，例如“打开哪个系统、选择哪个菜单、填写哪些字段、提交后看到什么结果”。如果某一步需要权限、审批、附件或等待时间，应直接写出来。截图只在能够帮助理解时使用，并定期确认截图中的界面、数据和链接仍然有效。

文档发布后要关注实际反馈。员工反复询问同一个问题，可能说明标题不容易搜索、关键前提隐藏在正文、流程本身不清楚或权限配置有问题。维护者应判断根因并更新正确位置，而不是在不同页面复制一段相同答案。

涉及制度变化时，旧版本应说明生效和废止时间，必要时保留变更摘要。对外部规则、费用标准、联系方式和系统入口，最好设置复审提醒。负责人离岗、部门调整或系统迁移后，及时转移维护责任，不能让文档因为没有主人逐渐失效。

知识库中的链接、标签和别名也需要治理。删除或移动文档前检查是否被其他流程引用，合并文档后更新入口。员工找到文档后仍然不知道下一步做什么，说明文档需要增加“快速开始”说明或明确的联系人，而不只是继续增加文字。

文档质量可以通过实际任务验证，而不是只看字数和格式。让一名不熟悉背景的员工按照文档完成一次操作，观察哪里需要反复询问、哪里容易误解、哪里缺少权限说明，再针对这些位置补充正文。这样增加的内容更有价值，也不会为了显得完整而堆叠无关章节。

维护者还应注意正文之间的前后一致。如果同一术语、系统名称、角色名称或步骤在不同文档中写法不同，员工会怀疑哪个版本才是正确的。可以建立常用术语表和核心入口，修改流程时同步检查相关文档，减少局部更新造成的矛盾。

持续用实际使用结果校正文档，才能让知识库长期保持可信、易找和可执行。
