# 数据分级与敏感信息处理规范

> 版本：V1.0｜适用对象：创建、使用、共享、存储或删除公司数据的全体人员。

## 1. 数据分级

在实际工作中，本节内容应作为后续流程的判断基础。员工遇到新情况时，先确认目标、事实和影响，再选择对应的处理方式；管理者应确保相关说明能够被员工找到、理解并执行。

数据级别应与实际影响相匹配，不能因为文件放在内部系统就默认风险很低，也不能因为数据量少就忽略敏感字段。无法判断时应向数据负责人说明内容和用途。

数据分级是为了让员工根据信息泄露、错误修改或不可用时的影响，选择合适的保护强度。公开信息、内部信息、机密信息和高度敏感信息的处理方式不同，但每个级别都需要明确责任人、使用目的和保存位置。

- **公开信息**：可对外发布且不产生明显风险的信息。
- **内部信息**：仅供公司内部使用的经营、流程和一般业务资料。
- **机密信息**：泄露可能造成业务、客户或竞争风险的信息。
- **高度敏感信息**：个人敏感信息、财务数据、密钥、源代码、未公开交易或重大安全信息。

## 2. 处理原则

具体适用时，应结合岗位、业务场景和风险程度判断，不宜只看表面形式。规则发生变化或现有说明无法覆盖时，及时向指定负责人确认，并把已经确认的处理方式记录下来，避免不同人员重复猜测。

项目负责人应在启动时确定数据流向和访问角色，人员加入、离开或业务范围变化时同步更新。权限和共享链接不能只在项目结束后才检查，否则风险可能已经持续很久。

本规范适用于创建、收集、使用、共享、导出、存储、归档和删除公司数据的人员。业务数据、客户资料、员工信息、财务数据、源代码、密钥和未公开经营信息都可能需要特殊保护。数据来源不明或级别不清时，不应直接转发或导出。

1. 按“业务必需、最小范围、授权访问、可追溯”原则处理数据。
2. 分享机密和高度敏感信息前，应确认接收人、用途、期限和传输渠道。
3. 使用导出、下载、打印和复制功能时，应评估必要性并保留审批或操作记录。
4. 对外发送文件前检查收件人、附件、链接权限和版本，必要时加密并设置有效期。
5. 不再需要的数据按保留期限和安全销毁流程处理，不得随意丢弃或恢复个人用途。

## 3. 发现误发

为便于落地，相关人员应明确谁提出、谁审批、谁执行、谁复核以及出现问题时找谁。流程运行一段时间后，根据员工反馈和实际异常补充说明，让制度逐步适应真实工作。

数据处理记录应让后来接手的人能够理解数据从哪里来、用于什么、存在哪里以及何时删除。记录不需要复杂，但必须足够支持复核和异常追踪。

数据负责人负责确定级别、用途、保存期限和访问范围，使用人员负责按批准方式处理，系统和安全人员负责提供权限、日志和保护措施。项目发生人员、范围或用途变化时，应重新确认数据责任，而不是默认原来的授权一直有效。

立即撤回或限制链接权限，通知直属经理、数据责任人和安全联系人，说明影响范围并保留证据。不得隐瞒或私下要求他人删除记录。

## 4. 检查清单

处理数据前先确认为什么需要、需要哪些字段、谁需要使用以及何时删除。共享时核对接收人和链接权限，导出时减少字段和范围，测试时使用脱敏或模拟数据。误发、丢失、越权访问和未授权导出应立即报告。

- [ ] 数据级别已识别
- [ ] 接收人和用途已核实
- [ ] 传输渠道符合安全要求
- [ ] 外发前已检查附件和权限
- [ ] 到期数据已按流程销毁

## 6. 数据识别方法

判断数据级别时，可以从内容、来源、使用范围和泄露后影响四个方面考虑。客户名单、员工薪酬、身份证件、密钥、未公开财务数据和源代码通常需要更高保护级别。无法判断时，应暂按较高等级处理，并向数据责任人咨询。

**创建与收集：**

开始收集数据前，先明确业务目的、必要字段、保存期限和使用人员。不要因为“以后可能有用”就大量收集信息。表单和系统字段应避免收集与目的无关的个人信息；确需新增字段时，应经过业务和隐私评估。

**共享与导出：**

共享前检查接收人是否确实需要、是否在授权范围内、是否使用批准渠道。文件名不应直接暴露完整身份证号、银行卡号或客户隐私。导出数据后应设置访问期限，任务结束后删除本地副本和临时压缩包。

**脱敏与使用示例：**

测试和培训尽量使用虚构数据。必须使用真实数据时，可遮挡姓名、联系方式、证件号、账号和地址等字段，并确保剩余字段不能轻易重新识别个人。截图、日志和演示文档也应按同样标准处理。

**常见异常：**

- **收件人填错**：立即撤回、限制访问并报告，不要只依赖对方口头承诺删除。
- **链接权限设为公开**：立即改为指定人员访问，检查访问记录并评估已暴露范围。
- **数据下载到个人设备**：停止继续使用，按指导安全删除并说明下载原因。
- **发现文件过期或来源不明**：不要继续传播，联系文档或数据负责人确认。

**数据生命周期：**

数据从创建、使用、共享、归档到删除都应有责任人。业务结束不代表数据可以立刻随意删除，需先确认法定保存、审计或争议保全要求。达到期限后，应使用可验证的删除、匿名化或介质销毁方式处理，并保留必要的处置记录。

**落地建议：**

团队可以为常见数据类型建立简单示例表，说明哪些内容属于内部、机密或高度敏感，以及应使用什么渠道共享。新项目启动时同步确定数据负责人和保存期限；项目结束时做一次数据清理，避免临时导出文件、共享链接和测试数据长期无人管理。

**员工自查：**

共享、导出或打印前先确认数据级别、接收人和保存期限。任务结束后删除临时副本，检查自己创建的链接和文件是否仍被需要；不确定是否可以发送时，先咨询数据负责人。

**复盘与改进：**

项目结束时检查哪些数据被重复导出、哪些权限长期保留，并将改进项加入下一次项目启动清单。

数据责任人应让使用者知道常见数据的分级、允许的存储位置和共享方式。可以在项目启动时给出几个正反例，例如哪些字段必须脱敏、哪些链接不能公开、哪些数据只能由指定角色访问。员工遇到新类型数据时，再根据内容和影响进行判断，不要机械套用旧案例。

同一份数据在不同阶段的风险可能不同。开发测试阶段需要严格限制真实数据，客户交付阶段要控制外发范围，归档阶段要关注保存期限和访问人员，删除阶段要确保副本、备份和共享链接也被处理。数据管理不能只关注上传和下载两个动作。

多人协作时，建议由一个负责人维护正式版本，其他人通过评论或变更记录提出修改。不要让多份导出表格在邮件和群聊中长期流转。需要临时协作时，设置访问期限和最小权限，工作结束后主动撤回，而不是等系统自动清理。

如果业务确实需要导出大量数据，应先明确范围、目的、审批、保存位置和完成后的删除方式。导出文件不要包含无关字段，不要通过个人电脑或个人云盘中转。处理完成后记录删除或归档情况，后续有人再次申请时可以复用合规结果。

数据误发后应尽快行动，因为链接撤回、账号冻结和接收方确认都会随时间变得更困难。报告时不要为了减少影响而缩小事实范围，宁可先提供已知信息，再由数据和安全负责人补充调查。组织应根据事件改进默认权限和提醒，而不只是要求员工以后更小心。

数据处理的好坏不仅体现在有没有发生泄露，也体现在是否收集了不必要的信息、是否让员工容易找到正确版本、是否能够在期限结束后删除，以及是否能在出现问题时快速还原过程。项目开始时把这些问题写进计划，通常比项目结束后补救更加省时。

对于跨部门项目，数据负责人应在启动时建立简单的共享清单，列出数据名称、级别、使用人、渠道和到期时间。项目成员发生变化或需求扩大时及时更新，避免原本合理的共享范围因为人员和任务变化而失控。

数据分级的目的不是增加形式化工作，而是帮助员工在不同风险下选择合适的保护方式。公开资料可以通过普通渠道发布，内部资料应限制在公司范围，机密和高度敏感信息则需要更严格的访问、传输、保存和删除控制。无法判断时，先按较高风险处理并向数据负责人咨询。

收集数据前应明确用途和必要字段，不要因为未来可能有用就把所有信息都收集下来。表单、导入模板和系统字段应定期清理，删除已经不再需要的字段。对个人信息、财务数据、密钥、源代码和未公开经营数据，应在项目开始时确定责任人和保存期限。

共享文件时，先核对接收人、业务目的、权限范围和有效期限。优先使用公司批准的协作空间，不要通过个人邮箱、个人网盘或公开链接传递敏感数据。文件名、截图和邮件主题也不要直接暴露完整证件号、银行卡号、客户名单或其他敏感内容。

导出数据时，应尽量限制字段、行数和时间范围，导出完成后及时清理本地副本、临时压缩包和下载目录。确需多人使用时，设置指定人员访问和到期时间。项目结束后检查共享链接、测试账号和导出文件是否仍然存在，必要时撤销并删除。

脱敏不能只删除姓名。联系方式、地址、订单号、时间和其他字段组合起来仍可能识别个人，因此培训、演示、测试和问题排查优先使用虚构数据或充分匿名化的数据。日志、屏幕截图、录屏和工单附件都可能含有敏感信息，应一并检查。

误发、权限设置错误、设备丢失或未授权导出发生后，应立即限制访问并报告。不要只依赖接收人承诺删除，也不要自行修改记录来掩盖问题。数据负责人、安全团队和隐私负责人需要根据日志判断哪些数据、多少人员和哪些系统受到影响。

把数据责任、使用边界和处理期限写清楚，才能让共享效率与保护要求保持平衡。
