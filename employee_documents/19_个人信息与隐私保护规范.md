# 个人信息与隐私保护规范

> 版本：V1.0｜适用对象：处理员工、客户、候选人、供应商联系人等个人信息的全体人员。

## 1. 处理原则

在实际工作中，本节内容应作为后续流程的判断基础。员工遇到新情况时，先确认目标、事实和影响，再选择对应的处理方式；管理者应确保相关说明能够被员工找到、理解并执行。

处理个人信息前应检查字段是否真的必要，不能因为系统默认有字段就全部填写。收集越多，后续访问、共享、保存和删除的责任越大，也越容易产生误发和越权风险。

个人信息保护的核心是只在明确、合法、必要的业务目的下处理信息，并尽量减少收集、访问、共享和保存范围。员工、客户、候选人和供应商联系人信息都应被当作需要谨慎处理的业务资料。

个人信息处理应具有明确、合法、必要的业务目的，遵循最小化、透明、安全和可追溯原则。不得因好奇、私人关系或非工作需要查询他人信息。

## 2. 收集与使用

具体适用时，应结合岗位、业务场景和风险程度判断，不宜只看表面形式。规则发生变化或现有说明无法覆盖时，及时向指定负责人确认，并把已经确认的处理方式记录下来，避免不同人员重复猜测。

数据用途、访问角色和保存期限发生变化时，应重新确认原有授权是否足够。项目扩大、供应商更换或新增分析用途，都不能直接沿用最初的范围。

本规范适用于招聘、员工管理、客户服务、市场活动、运营分析、系统测试、供应商协作和离职交接等场景。不同场景所需字段和保存期限可能不同，但不得因为信息存放在表格、日志、截图或聊天记录中就降低保护要求。

1. 仅收集完成业务所必需的信息，并说明用途、保存期限和使用范围。
2. 使用个人信息开展分析、测试或演示时，优先使用脱敏、匿名化或模拟数据。
3. 需要向第三方提供信息时，应确认授权、合同、用途、范围和安全措施。
4. 不通过个人邮箱、个人网盘或未批准工具存储、传输个人信息。

## 3. 权限与保存

为便于落地，相关人员应明确谁提出、谁审批、谁执行、谁复核以及出现问题时找谁。流程运行一段时间后，根据员工反馈和实际异常补充说明，让制度逐步适应真实工作。

员工收到个人信息请求时，应先核验身份并转交指定负责人，不要在公开群组中讨论。任何删除、更正或共享承诺都应由有权限的部门确认并留下记录。

业务负责人负责明确目的和数据范围，使用人员负责按权限处理，系统和安全人员负责访问、日志和保护措施，隐私或法务负责人负责复杂场景和权利请求。涉及第三方、跨系统或新用途时，应提前评估，而不是收集后再补手续。

个人信息应存放在受控系统中，限制下载、导出和打印权限。达到保存期限或处理目的完成后，应按要求删除、匿名化或归档。

## 4. 事件处理

收集前说明用途和必要字段，使用时限制访问和导出，分享时核对接收人和期限，任务结束后删除或匿名化。测试和演示优先使用模拟数据。误发、丢失、越权访问和未授权导出应立即报告，不要自行隐瞒或承诺结果。

误发、丢失、越权访问、未授权导出或收到个人信息权利请求时，应立即通知隐私或安全负责人，不得自行承诺处理结果或隐瞒影响。

## 5. 检查清单

- [ ] 处理目的和必要性已明确
- [ ] 使用了最小范围的数据
- [ ] 测试和演示优先使用脱敏数据
- [ ] 访问权限已限制并可追溯
- [ ] 隐私事件已及时报告

**处理个人信息前的判断：**

开始收集或使用个人信息前，先回答：为什么需要这些信息，哪些字段是必须的，谁需要访问，保存多久，使用结束后如何处理。如果只需要统计结果，就不要收集可以识别个人的明细。对用途不清、来源不明或过度收集的数据，应先咨询隐私或法务负责人。

**员工和客户信息使用：**

招聘、薪酬、考勤、客户服务、市场活动和售后支持都可能涉及个人信息。员工只能在职责范围内查看信息，不因为认识某人、好奇或私人请求查询其记录。向客户或员工回复信息时，应核实身份，避免把内容发送给同名或未经授权的联系人。

**委托和第三方共享：**

向供应商、云服务商、外包团队或合作伙伴提供个人信息前，应确认业务必要性、共享字段、使用目的、保存期限和安全责任。第三方人员变更、项目结束或合同终止后，应及时回收访问权限并确认资料返还或删除。

**脱敏和测试：**

演示、培训、开发和问题排查优先使用假名、随机编号、遮挡字段或完全模拟的数据。仅删除姓名并不一定足够，多个字段组合后仍可能识别个人。日志、截图、录屏、邮件附件和导出表格都要检查是否含有个人信息。

**权利请求和事件处理：**

收到查询、更正、删除、撤回授权或其他个人信息请求时，不要自行承诺一定满足，也不要直接删除系统记录。先确认请求人身份和请求内容，转交隐私负责人处理。发生误发、越权访问、丢失或未授权导出时，应立即报告时间、数据类型、涉及人数和已采取措施。

**日常自检：**

发送文件前确认收件人，导出数据前确认用途，离开工位前锁屏，任务结束后清理临时副本。对不确定的场景，先暂停共享并咨询，不要以“大家都这么做”作为继续处理的理由。

**落地建议：**

各部门可以列出自己最常处理的个人信息类型、使用系统、负责人和常见风险，作为简短操作卡。系统上线、营销活动、员工调查和供应商接入前，提前把隐私要求放进需求评审，而不是等数据已经收集后才补救。员工遇到疑问时，应优先寻求指导。

**员工自查：**

处理个人信息前确认目的、范围和接收人，发送前再次核对身份和附件。工作结束后删除临时副本，发现误发、丢失或越权访问立即报告，不自行隐瞒或承诺处理结果。

**复盘与改进：**

部门可根据误发、权限和供应商反馈更新操作卡与系统提示，让个人信息保护成为日常流程的一部分。

处理个人信息前先确认业务目的、必要字段、使用人员、保存期限和处理方式。只需要统计结果时，不要收集能够识别个人的明细；只需要联系方式时，不要顺便收集与业务无关的家庭、健康或身份信息。收集范围越小，后续保护和删除越容易。

员工只能在职责范围内查询和使用个人信息，不因为好奇、私人关系或他人请求查看记录。向员工、客户或候选人回复信息前核实身份和接收渠道，避免因为同名、自动补全或错误群组把内容发送给无关人员。

向供应商、云服务商、外包团队或合作伙伴共享信息时，应确认共享目的、字段范围、保存期限、访问人员和安全责任。项目结束、人员变更或合同终止后回收访问权限，并根据要求确认资料返还、删除或匿名化。

测试、培训、演示和问题排查优先使用模拟数据。仅删除姓名不一定足够，联系方式、地址、时间、订单和其他字段组合后仍可能识别个人。日志、截图、录屏、邮件附件和导出表格都要按个人信息处理，不要因为它们是“临时材料”就忽略风险。

收到查询、更正、删除、撤回授权或其他个人信息请求时，不要自行承诺一定满足，也不要直接修改或删除系统记录。先确认请求人身份和请求内容，再转交隐私负责人。发生误发、丢失、越权访问或未授权导出时，应报告涉及的数据类型、人数、时间和已采取措施。

隐私保护不应只依赖员工记忆。系统可以通过默认权限、字段最小化、下载限制、链接到期、日志记录和提醒减少错误。部门应定期复查常用表单、供应商和共享空间，发现收集过度、长期保留或权限过宽时及时整改。

个人信息进入系统前，应明确由哪个部门负责、谁可以查看、谁可以导出、谁可以修改和谁负责删除。职责不清时，出现误发或请求时容易互相推诿。项目负责人可以在需求文档中记录数据流向，从收集入口一路标到使用系统、第三方和归档位置。

向员工或客户说明信息使用方式时，语言应清晰易懂，不要把重要内容藏在长篇条款或模糊的“其他用途”中。业务目的发生变化时，重新评估是否仍然可以使用原数据。新增分析、营销或模型训练用途时，不能默认原来的收集授权自动覆盖。

第三方共享前应确认对方的安全能力、访问人员、保存地点、分包关系和事件通知方式。合同和技术措施都要能落地，例如账号是否实名、权限是否到期、数据是否加密、项目结束如何删除。供应商无法说明这些问题时，不应先把数据发出去再补文件。

员工收到个人信息权利请求时，不要把请求直接转发到公开群组，也不要自行判断请求人是否有权访问全部内容。先核实身份并转交隐私负责人，保留原始请求和处理时间。任何承诺都应由有权限的部门作出，避免业务人员无意中扩大义务。

隐私事件处理结束后，除了关闭当前账号或删除当前文件，还要检查是否存在邮件、缓存、备份、下载、截图和第三方副本。根据风险决定是否需要通知相关人员或监管机构，并把原因和处理过程记录下来。复盘应关注为什么系统允许错误发生，以及如何让下一次更难发生。

个人信息保护应在需求、采购、开发、运营、客服和离职交接等环节提前考虑，而不是只由隐私负责人在最后审批。员工能够说清楚为什么收集、谁能使用、何时删除和发生问题找谁，就说明流程已经具备了基本的可执行性。

如果业务人员发现某个表单字段无人使用、某个共享链接长期公开、某个供应商仍保留历史数据，应主动提出清理或复核。隐私保护不是阻止正常业务，而是帮助组织用更少、更准确、更受控的数据完成同样的业务目标。

从源头减少不必要的收集和共享，是比事后补救更稳定、更低成本的保护方式。
