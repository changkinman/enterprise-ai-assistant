# 账号密码与多因素认证规范

> 版本：V1.0｜适用对象：使用公司信息系统的所有人员。

## 1. 账号使用原则

在实际工作中，本节内容应作为后续流程的判断基础。员工遇到新情况时，先确认目标、事实和影响，再选择对应的处理方式；管理者应确保相关说明能够被员工找到、理解并执行。

账号申请应与岗位职责和项目周期对应，审批人不能只看申请人是谁，还要看申请了什么权限、为什么需要以及何时不再需要。申请内容越具体，后续复核越容易。

账号是员工在公司系统中的实名工作身份，账号操作应能够追溯到实际使用人。密码、多因素认证设备、恢复码和访问令牌都属于敏感凭证，任何人不得因为工作方便而共享、转发或保存在公开位置。

账号实行实名制和最小权限原则。员工只能使用本人账号，禁止借用、出租、转让或共享账号；服务账号由指定管理员管理。

## 2. 密码要求

具体适用时，应结合岗位、业务场景和风险程度判断，不宜只看表面形式。规则发生变化或现有说明无法覆盖时，及时向指定负责人确认，并把已经确认的处理方式记录下来，避免不同人员重复猜测。

密码和认证设备应被视为个人工作资产，员工离开工位、换设备或长期休假时要确认账号仍处于安全状态。任何要求提供验证码或远程代登录的请求都应先验证身份。

本规范适用于邮箱、办公系统、代码仓库、财务系统、客户系统、管理后台和第三方平台等所有公司账号。临时账号、服务账号和外部协作账号也必须有明确用途、责任人、权限范围和失效时间，不能因为不属于员工个人账号就放松管理。

1. 使用长度足够、难以猜测且不同系统不重复的密码或密码短语。
2. 不使用姓名、生日、手机号、公司名称、连续数字或公开信息作为密码。
3. 不将密码写在便签、聊天窗口、代码仓库或未加密文档中。
4. 怀疑密码泄露时，立即修改密码并通知 IT；不得继续使用疑似泄露的密码。
5. 允许使用的密码管理器应由公司批准并启用设备保护。

## 3. 多因素认证

为便于落地，相关人员应明确谁提出、谁审批、谁执行、谁复核以及出现问题时找谁。流程运行一段时间后，根据员工反馈和实际异常补充说明，让制度逐步适应真实工作。

管理员应把临时权限、紧急权限和高权限操作区分管理，并设置到期、复核和日志要求。这样既能支持紧急业务，也能避免临时安排长期存在而无人负责。

员工负责保护本人凭证并报告异常，经理负责确认业务需要和权限范围，系统管理员负责开通、变更、复核与回收。审批人应判断最小权限是否足够，管理员应按批准内容实施，不能以口头请求长期授予高权限。

访问邮箱、代码仓库、财务系统、管理后台等高风险系统时，必须启用多因素认证。验证码、硬件令牌和恢复码均属于敏感凭证，不得提供给他人。

## 4. 离职与权限变更

密码应独立、难猜且不在不同系统重复使用；多因素认证应覆盖高风险系统和管理操作。收到未发起的登录推送、验证码或安全提醒时，不要点击批准，也不要把验证码告诉任何人，应保留信息并通过正式渠道处理。

岗位变更、长期休假、外包结束或离职时，应及时回收、调整或冻结权限。发现异常登录时，员工应保留通知内容并立即联系 IT。

## 5. 检查清单

- [ ] 使用个人实名账号
- [ ] 不同系统未重复使用密码
- [ ] 高风险系统已启用多因素认证
- [ ] 凭证未保存在公开位置
- [ ] 权限变更已及时申请

**账号申请与开通：**

新员工、岗位变更、项目临时成员和外部协作人员都应通过统一流程申请账号。申请内容应说明使用人、系统、业务目的、所需权限、起止时间和审批人。管理员不应仅凭聊天消息长期开通高权限账号；紧急开通也应在事后补齐记录。

**权限使用习惯：**

账号权限只用于已批准的工作，不借用他人账号代办业务，不使用他人登录状态进行敏感操作。需要临时代办时，应通过授权、代理或工单机制完成。员工离开岗位、项目结束或工作范围变化时，应主动检查是否仍保留不必要的权限。

**密码和凭证保管：**

密码管理器、硬件密钥和恢复码应存放在个人可控且受保护的位置。不要把凭证写进源代码、脚本、截图、邮件或会议录屏。共享服务若必须使用密钥，应采用公司批准的密钥管理方式，设置轮换周期和责任人。

**多因素认证异常：**

如果收到自己没有发起的登录确认、验证码或推送请求，应拒绝并立即检查账号安全。短时间反复收到推送可能意味着攻击者已经掌握密码。不要为了“让通知停止”而随意批准请求，也不要把验证码告诉自称 IT、银行或供应商的人员。

**账号异常处理：**

- **忘记密码**：使用正式找回流程，不向同事索取密码。
- **设备丢失**：立即报告并说明设备、账号和最后使用时间，配合远程锁定。
- **发现陌生登录**：保留登录通知和时间信息，修改密码并联系 IT。
- **权限不足**：说明业务需要和期限，通过审批申请，不自行寻找绕过方式。
- **人员离职或转岗**：经理、人力资源和 IT 应同步触发权限回收或变更。

**管理员责任：**

管理员应定期复核高权限账号、共享账号、长期未使用账号和临时权限。系统日志应能追溯关键操作的使用人。发现账号长期无人维护、权限明显超出工作需要或认证方式失效时，应及时整改。

**落地建议：**

员工可以每季度检查一次自己使用的系统，关闭不再需要的旧账号，更新恢复联系方式，并确认多因素认证设备仍可用。团队新增系统时，应在上线前确定账号所有者、权限审批人和离职回收方式，避免系统运行后才发现没有人负责维护。

**员工自查：**

不要批准自己没有发起的登录推送，不要把验证码告诉任何人。岗位变化、项目结束或长期休假前，主动确认权限是否需要回收；发现陌生登录时保留通知并立即走正式报告渠道。

**复盘与改进：**

系统管理员应根据异常登录、锁定和权限申请情况优化认证提示与回收流程，让正确操作更容易完成。

账号管理应覆盖完整生命周期：申请、审批、开通、使用、变更、暂停和回收。申请人要说明业务目的和期限，审批人要判断权限是否必要，管理员要按批准范围实施，使用人要对账号活动负责。任何一个环节缺少记录，后续都很难判断权限是否仍然合理。

最小权限不是让员工无法工作，而是只开放完成当前职责所需的范围。普通查询、数据导出、配置修改和管理员操作应尽量分开。临时高权限应设置到期时间，长期需要时重新审核，不应因为“以后可能有用”就永久保留。

密码和多因素认证是不同层次的保护。密码应独立、难猜且不重复使用，多因素认证设备和恢复码也要受到保护。收到自己没有发起的推送时，不要为了停止通知而点击批准；应拒绝请求、修改密码并报告异常。

共享账号会削弱追溯和责任确认，因此应优先改为实名账号、代理机制或受控服务账号。确实无法避免的服务账号，应由明确的责任人保管凭证，限制登录来源，记录关键操作并在人员变更时及时轮换。

岗位变更、项目结束、长期休假和外包终止都是权限复核节点。经理应说明员工的新职责和不再需要的系统，IT 应同步调整邮箱、代码仓库、VPN、财务、客户和管理后台权限。员工自己也应主动提醒，不要把权限回收完全当作别人的责任。

账号异常处理时，保留登录时间、设备、地点和通知内容等信息。若设备丢失，应说明设备编号、最后使用时间和可能存储的数据；若怀疑密码泄露，应按指导修改密码并检查相关系统，而不是只修改一个最常用的账号。管理员应定期复核长期未使用账号和高权限账号。

新系统上线时，应在需求阶段就确定登录方式、账号所有者、权限角色、认证强度和回收触发条件。不要等系统投入使用后才补充账号管理。对外部平台和第三方账号，也应登记业务负责人和公司邮箱，避免人员离职后无人能够管理。

员工忘记密码时使用正式找回流程，不通过同事代登录或临时共享账号解决。管理员重置密码前应核验申请人身份，并尽量让员工在首次登录后立即修改。恢复码和备用认证方式应由员工本人妥善保管，不能截图发送给他人。

高风险系统可以采用分级认证，例如普通查询使用常规登录，导出大量数据、修改权限和执行管理操作需要更强的多因素认证或二次审批。认证要求应与实际风险匹配，既不能对低风险事项设置过多阻碍，也不能让高风险操作只依赖一个密码。

共享服务账号如确实存在，应限制使用范围、登录来源和可执行动作，并通过密钥管理工具轮换凭证。不要把服务账号密码写在部署文档、脚本仓库或群聊里。服务账号负责人、用途和失效条件应有清晰记录，系统迁移后及时清理旧凭证。

权限复核不应只是点击“确认全部正确”。审批人应抽查高权限和临时权限，确认员工实际工作仍需要这些权限。发现长期没有使用、职责已经变化或无法确认所有者的权限，应先暂停或重新申请，避免历史配置持续扩大风险。

员工遇到权限不足时，应说明需要完成的业务动作和预计使用期限，帮助审批人判断真正需要的范围。管理员可以提供只读、临时或受限替代方案，不必直接授予最高权限。权限申请越清晰，审批越容易，也越能减少后续回收和审计中的争议。

权限问题如果长期依靠熟人代办，说明系统角色或流程可能需要改进。团队应把重复出现的申请整理成标准角色，明确申请材料和审批人，让员工能够通过公开、可追溯的方式获得工作所需权限，而不是依赖私下共享账号或临时放开管理员权限。

通过清晰的角色、期限和责任人管理权限，能够在不影响效率的情况下持续降低账号风险。
