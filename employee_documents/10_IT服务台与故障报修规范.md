# IT 服务台与故障报修规范

> 版本：V1.0｜适用对象：全体员工；适用于账号、设备、网络、软件和系统使用问题。

## 1. 报修渠道

在实际工作中，本节内容应作为后续流程的判断基础。员工遇到新情况时，先确认目标、事实和影响，再选择对应的处理方式；管理者应确保相关说明能够被员工找到、理解并执行。

报修入口应让员工容易找到，优先级、响应方式和紧急联系人也应公开说明。员工知道不同问题应该走什么渠道，IT 才能更快分配和处理。

IT 服务台是员工处理账号、设备、网络、软件和系统问题的统一入口。统一报修可以帮助团队判断影响范围、安排优先级、保留记录和复盘根因，也能避免员工各自寻找未经批准的解决办法。

优先通过公司服务台、工单系统或指定邮箱报修。涉及账号泄露、恶意软件、数据误发、设备丢失等安全事件，应同时使用紧急联系人渠道，不等待普通工单排队。

## 2. 工单内容

具体适用时，应结合岗位、业务场景和风险程度判断，不宜只看表面形式。规则发生变化或现有说明无法覆盖时，及时向指定负责人确认，并把已经确认的处理方式记录下来，避免不同人员重复猜测。

工单内容要围绕事实和影响，不要只写“系统坏了”或“很急”。说明具体操作、错误现象和受影响的业务，可以明显减少服务台反复追问的时间。

本规范适用于所有员工和使用公司 IT 资源的第三方。普通功能咨询、单点故障、批量中断、安全事件、设备丢失和数据误发可以采用不同优先级，但安全事件和重大业务中断不应等待普通工单队列。

提交工单时应提供：问题现象、发生时间、影响范围、复现步骤、错误截图或日志、设备编号、联系方式和已尝试措施。不得在工单中明文提交密码、验证码或完整密钥。

## 3. 优先级参考

为便于落地，相关人员应明确谁提出、谁审批、谁执行、谁复核以及出现问题时找谁。流程运行一段时间后，根据员工反馈和实际异常补充说明，让制度逐步适应真实工作。

重大故障期间应有统一的进度更新和对外口径，避免不同群组传播互相矛盾的信息。恢复后还要说明临时措施是否仍有效，以及员工是否需要补做操作。

员工负责提供真实、完整、脱敏的现象和影响，IT 负责确认、跟进、处理和说明恢复结果，业务负责人负责确认业务优先级和临时方案。远程协助和权限操作应通过正式工单建立联系，双方都要保护账号和敏感信息。

- **紧急**：核心系统大面积不可用、安全事件或造成重大业务中断。
- **高**：关键岗位无法工作、重要客户服务受影响或多个用户受影响。
- **普通**：单个用户功能异常，有可行临时替代方案。
- **低**：咨询、优化建议或非紧急配置申请。

## 4. 配合要求

工单至少应说明发生时间、问题现象、影响范围、复现步骤、设备或系统、错误信息和已尝试操作。问题恢复后确认业务结果；如果故障反复发生、临时方案不安全或影响仍未消除，应继续在原工单中补充信息。

员工应及时回复 IT 的澄清问题，按指导提供远程协助或到指定地点处理。故障恢复后确认结果；若问题重复发生，应补充发生频率和影响。

## 5. 检查清单

- [ ] 使用正确报修渠道
- [ ] 已描述影响范围和复现步骤
- [ ] 未提交密码或验证码
- [ ] 安全事件已走紧急通道
- [ ] 故障恢复后已确认并关闭工单

**报修前的快速检查：**

提交工单前，可先确认电源、网络、设备重启、账号状态和是否只有自己受到影响。快速检查不是要求员工自行修复所有问题，而是帮助 IT 更快判断范围。涉及安全事件、数据丢失或设备丢失时，不要为了“先试试”而删除日志或反复重置设备。

**工单描述模板：**

建议按以下顺序描述：

1. **现象**：看到什么错误或无法完成什么操作。
2. **时间**：首次发生时间、频率和是否持续。
3. **影响**：影响个人、团队、客户还是核心业务。
4. **复现**：按什么步骤可以再次出现。
5. **环境**：设备、系统、浏览器、网络和最近变更。
6. **附件**：截图、错误编号和脱敏日志，不附带密码或敏感数据。

**工单跟进：**

员工应在工单中补充最新现象，不要重复创建多个相同工单。问题恢复后，确认业务是否真正恢复，而不只是“页面能打开”。若临时方案影响效率或安全，应继续反馈并推动根因修复。

**远程协助注意事项：**

接受远程协助前确认对方是公司 IT 或授权服务商，并通过正式工单建立联系。远程操作期间不要输入密码、验证码或打开与问题无关的敏感文件。协助结束后关闭远程工具和临时权限，发现异常操作立即停止并报告。

**常见场景处理：**

- **邮箱无法登录**：记录错误提示和最近是否修改过密码，不要连续尝试导致账号锁定。
- **网络缓慢**：说明影响的系统、地点、设备和开始时间，帮助判断是单点还是区域问题。
- **系统功能异常**：提供业务操作步骤和预期结果，必要时附脱敏截图。
- **设备丢失或被盗**：优先拨打紧急联系人并说明设备编号，随后补充正式工单。

**服务改进：**

IT 可根据重复工单、平均解决时间和用户反馈更新知识库、常见问题说明和自动化工具。员工发现说明文档过期、步骤不清或同一问题反复发生时，也可以通过工单提出改进建议。

**落地建议：**

员工不必记住所有技术术语，只要能清楚说明现象、影响和时间即可。IT 服务台可以在工单页面提供示例、优先级说明和敏感信息提示；业务部门则应指定关键系统联系人，出现大面积故障时快速确认影响范围和恢复优先级。

**员工自查：**

报修前记录错误信息和发生时间，不在工单中填写密码、验证码或完整密钥。问题恢复后确认业务结果并关闭工单；如果同一故障反复发生，补充频率和影响，帮助 IT 处理根因。

**复盘与改进：**

服务台可定期查看重复工单和用户反馈，更新知识库与自动化处理；员工也可以直接指出说明文档中难以理解的步骤。

提交工单时不需要使用复杂的技术术语，但要尽量描述可观察的事实。说明无法完成什么操作、何时开始、是否持续、影响几个人、错误提示是什么、最近是否发生变更，以及有没有临时替代方案。截图和日志应先脱敏，密码、验证码和完整密钥绝不能写入工单。

优先级应根据业务影响而不是个人焦虑判断。核心系统大面积不可用、安全事件和重大客户影响需要紧急处理；单个用户有替代方案的问题可以按普通优先级排队。若影响范围扩大，员工应在原工单中更新信息，不要反复创建多个相同工单。

IT 远程协助前，员工应确认对方来自正式服务台或授权供应商，并通过工单建立联系。远程操作时不要输入密码、验证码或打开无关敏感文件，协助结束后关闭临时工具和权限。发现对方要求绕过流程、索要凭证或执行与问题无关的操作时，应立即停止。

故障恢复不只意味着页面重新打开，还要确认业务结果、数据完整性和后续操作是否正常。员工确认恢复后可以关闭工单，但如果问题反复、临时方案影响效率或仍存在安全风险，应继续反馈并要求根因处理。关闭工单前补充结果，有助于后续统计和知识库维护。

安全事件、设备丢失、数据误发和疑似恶意软件不应等待普通队列。先按紧急渠道报告，再补充工单编号和详细材料。报告时说明发生时间、设备或系统、可能涉及的数据、已经采取的措施和当前是否仍在扩大，避免只写“系统有问题”。

服务台可以根据重复问题制作短指南和自动化检查，但指南应定期复审。系统改版、账号流程变化和安全策略调整后，旧文档应及时更新。员工发现知识库步骤失效时，应在工单中指出具体位置，这比重新寻找非官方教程更安全。

提交工单后，员工应关注服务台的补充问题和通知，不要因为暂时没有新消息就重复创建工单。如果联系人、影响范围或错误现象发生变化，应在原工单中更新。多个部门共同受影响时，项目或业务负责人可以统一汇总影响，减少 IT 收到互相矛盾的信息。

IT 需要远程查看屏幕、日志或设备时，应说明目的和预计操作。员工可以要求对方通过正式工单确认身份，也可以在敏感操作前暂停并询问。远程支持结束后，双方确认临时权限、共享链接和下载文件已经关闭或删除。

核心系统故障期间，员工不要自行修改生产配置、绕过审批或把客户数据复制到个人工具中寻找替代方案。业务负责人应与 IT 确认临时流程、优先级和对外口径。故障恢复后，再安排补录、数据核对和根因修复，避免临时方案成为长期风险。

服务台可以按问题类型设置标准信息，例如账号问题需要用户、系统和错误提示，网络问题需要地点和设备，软件问题需要版本和复现步骤。标准信息不是为了拒绝工单，而是减少往返沟通，让技术人员更快进入处理阶段。

员工对服务结果有疑问时，应具体说明哪里仍未恢复、影响什么工作以及希望验证的结果。IT 关闭工单后，如果同一问题再次出现，可以关联原工单并补充新的时间和现象。持续反馈有助于区分偶发故障、配置问题和系统性缺陷。

服务台与业务部门应把故障处理看成共同解决问题的过程。员工提供准确现象和影响，IT 提供进度、临时方案和风险说明，负责人在必要时帮助确认业务优先级。信息保持同步，才能避免技术已经恢复但业务仍无法继续，或业务已经绕行但系统团队不知道真实影响。

故障结束后还应确认用户是否知道临时方案何时失效、正式修复是否完成以及后续是否需要补录数据。对于影响多个团队的问题，发布统一的恢复说明和注意事项，避免不同人员根据过时消息继续操作。清晰的结束标准能减少同一故障反复打开。

持续反馈真实使用情况，能够帮助服务台不断缩短处理时间并提高解决质量。
